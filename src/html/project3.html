Plateforme web & bots Discord

Dans le cadre de la gestion d’un serveur Rust moddé, j’ai participé à la conception et au développement d’un dashboard web permettant de centraliser la gestion des joueurs, des avantages VIP et des interactions communautaires.

L’application repose sur une API Fastify (Node.js) et un dashboard rendu côté serveur en EJS, avec Prisma ORM connecté à une base PostgreSQL pour le stockage structuré des informations utilisateurs (identifiants Discord et Steam, statut VIP, historique d’activité, récompenses, etc.).

Un système d’authentification sécurisé via OAuth2 (Discord et Steam) a été implémenté afin de permettre aux utilisateurs de se connecter avec leur compte Discord et d’associer automatiquement leur identité Steam, créant ainsi une liaison multi-comptes synchronisée avec le serveur de jeu. Les jetons OAuth sont chiffrés au repos (AES-256-GCM) avant d’être stockés en base.

Le Dashboard intègre plusieurs logiques

  • • Suivi automatisé du play streak journalier avec réinitialisation conditionnelle en cas d’inactivité.
  • • Gestion dynamique du statut VIP (durée, fidélité, récompenses progressives).
  • • Attribution automatisée d’avantages en jeu (priorité dans la file d’attente, bonus, permissions spécifiques).
  • • Synchronisation avec le serveur Rust pour appliquer les permissions et paramètres en temps réel.
  • • Interaction avec l’API Discord pour l’attribution de rôles et avantages communautaires, et ajout automatique au serveur Discord après la première connexion.
  • • Profils « explorateur » temporaires : un joueur qui rejoint le serveur sans compte garde sa progression (streak) jusqu’à ce qu’il lie son compte sur le dashboard.
  • • Boutique Tebex : chaque paiement arrive par webhook, vérifié par signature HMAC-SHA256 et liste blanche d’adresses IP, puis enregistré dans un registre d’achats. Un webhook reçu deux fois ne donne jamais deux fois la récompense, et le VIP acheté est activé automatiquement en jeu et sur Discord.

L’architecture combine gestion base de données relationnelle, logique algorithmique côté serveur (Node.js), automatisation de récompenses conditionnelles et communication inter-systèmes (serveur Rust ↔ base de données ↔ Discord API).

Sécuriser l’API

L’API est exposée sur Internet et reçoit à la fois des joueurs, des plugins de jeu et des paiements : chaque type d’appel a donc sa propre protection.

  • • Plugins du jeu : une clé d’API transmise dans un en-tête et comparée en temps constant, pour qu’on ne puisse pas la deviner caractère par caractère en mesurant le temps de réponse.
  • • Pages d’administration : réservées aux comptes Discord d’une liste d’administrateurs. Un visiteur non connecté reçoit une erreur 404 au lieu de 403, ce qui rend ces pages invisibles aux scanners.
  • • Données reçues : chaque requête est validée par un schéma (zod) et rejetée si sa forme est incorrecte.
  • • En-têtes de sécurité : Content-Security-Policy, HSTS, protection contre l’intégration dans une iframe, via Helmet.
  • • Routes de développement : elles ne sont tout simplement pas enregistrées en production.
  • • Limitation de débit sur les routes publiques, et jetons OAuth chiffrés en AES-256-GCM.

Côté Discord, les bots ont des responsabilités séparées : un bot global (le Sentinel) pour tout ce qui concerne la communauté, puis un bot par serveur de jeu (production et staging), chacun dans son propre conteneur.

Le bot Purple, celui du serveur de production, gère le système de vote dynamique des maps (qui sont votées par les joueurs à chaque fois que la partie repart à zéro sur le serveur du jeu) via des interactions Discord (boutons API), avec les cartes proposées récupérées depuis l’API RustMaps. C’est aussi lui qui déclenche le processus de wipe (voir page suivante).

Chaque vote est pondéré en fonction de plusieurs critères stockés en base de données : statut VIP du joueur (avec bonus progressif selon le nombre de mois cumulés que la personne est abonnée à l’offre) et interactions passées.

La logique calcule dynamiquement un poids de vote basé sur ces paramètres, puis met à jour ou crée l’enregistrement correspondant via des opérations upsert Prisma afin de garantir l’idempotence et permettre la modification des votes sans duplication.

Il intègre également

  • • Un système de prévention de duplication via lock file pour éviter les instances concurrentes.
  • • Une gestion mémoire temporaire des messages traités pour éviter le double traitement.
  • • Des requêtes agrégées (groupBy) pour recalculer en temps réel les résultats pondérés.

Une file d’attente par tirage pondéré

Quand le serveur est plein, les joueurs patientent dans une file d’attente. Plutôt qu’un simple « premier arrivé, premier servi », le plugin maison RustianQueue (C#) fait un tirage au sort pondéré : l’API lui fournit le poids de chaque joueur selon son statut VIP et sa streak.

  • • Le plugin ne touche jamais au joueur en première position (« YOU’RE NEXT »), ni à la place réservée pendant 5 minutes après un crash, gérée nativement par Rust.
  • • Le joueur tiré au sort est placé juste derrière, en deuxième position.
  • • Si le plugin n’arrive plus à lire la file interne du jeu (après une mise à jour de Rust par exemple), il passe en mode dégradé et laisse la file normale fonctionner au lieu de la bloquer.
  • • Chaque décision est tracée et conservée 24 h dans Redis, pour pouvoir expliquer à un joueur pourquoi il a attendu.

Contrairement au bot Purple, orienté interaction utilisateur, le Bot Master fonctionne principalement en arrière-plan via des tâches planifiées, garantissant la synchronisation continue des statuts VIP, des streaks et des rôles Discord. Il s’occupe aussi du suivi de l’état des serveurs, des annonces de mises à jour officielles de Rust (flux RSS de Facepunch, vérifié toutes les 30 minutes), du relevé des métriques et du nettoyage des anciennes données.

Les extraits de code ci-dessous sont la première version de deux de ces tâches. Elles ont été renforcées depuis (voir plus bas).

Un processus planifié s’exécute toutes les 15 minutes afin de

  • • Identifier les utilisateurs éligibles à des privilèges (VIP global, VIP serveur, streak ≥ 7 jours, Nitro Boost).
  • • Effectuer une requête relationnelle incluant une sous-requête sur les VIP serveur.
  • • Réunir les utilisateurs actifs devant posséder un rôle.
  • • Déclencher un service dédié (RoleSyncService) chargé d’appliquer les rôles Discord correspondants.
💻 Voir le code — Sentinel de synchronisation des rôles (V1) 
import cron from 'node-cron';
import { PrismaClient } from '@prisma/client';
import { RoleSyncService } from '../services/RoleSyncService';
const prisma = new PrismaClient();
export function scheduleRoleSync(roleSync: RoleSyncService) {
    cron.schedule('*/15 * * * *', async () => {
        console.log('[Cron] Sentinel: Starting periodic role sync...');
        const serverVipUsers = await prisma.serverStats.findMany({
            where: { isVip: true },
            select: { userId: true }
        });
        const serverVipIds = serverVipUsers.map(s => s.userId);
        const activeUsers = await prisma.user.findMany({
            where: {
                OR: [
                    { isGlobalVip: true },
                    { globalStreak: { gte: 7 } },
                    { isNitroBoosting: true },
                    { discordId: { in: serverVipIds } }
                ]
            }
        });
        console.log(`[Cron] Sentinel: Syncing ${activeUsers.length} active users...`);
        for (const user of activeUsers) {
            await roleSync.syncUser(user.discordId);
            await new Promise(r => setTimeout(r, 1000));
        }
        console.log('[Cron] Sentinel: Sync complete.');
    });
    console.log('[Cron] Role Sync Sentinel scheduled (every 15m).');
}

Ce mécanisme agit comme un système de réconciliation, garantissant que les rôles Discord reflètent toujours l’état réel en base de données, même en cas d’erreur, de redémarrage ou de désynchronisation temporaire.

Une seconde tâche planifiée s’exécute quotidiennement à minuit (timezone Europe/Paris) afin de

  • • Identifier les utilisateurs dont l’abonnement VIP global est expiré.
  • • Mettre à jour automatiquement leur statut en base de données.
  • • Déclencher immédiatement une synchronisation de rôles pour retirer les privilèges associés.
💻 Voir le code — Expiration automatique des VIP (V1) 
import cron from 'node-cron';
import { PrismaClient } from '@prisma/client';
import { RoleSyncService } from '../services/RoleSyncService';
const prisma = new PrismaClient();
export function scheduleVipExpiration(roleSync: RoleSyncService) {
    cron.schedule('0 0 * * *', async () => {
        console.log('[Cron] Checking for expired VIPs...');
        const now = new Date();
        try {
            const expiredUsers = await prisma.user.findMany({
                where: {
                    isGlobalVip: true,
                    globalVipExpiresAt: {
                        lt: now
                    }
                }
            });
            if (expiredUsers.length === 0) {
                console.log('[Cron] No expired VIPs found.');
                return;
            }
            console.log(`[Cron] Found ${expiredUsers.length} expired VIPs. Processing...`);
            for (const user of expiredUsers) {
                await prisma.user.update({
                    where: { discordId: user.discordId },
                    data: {
                        isGlobalVip: false
                    }
                });
                console.log(`[Cron] Expired VIP for ${user.username} (${user.discordId})`);
                await roleSync.syncUser(user.discordId);
            }
        } catch (error) {
            console.error('[Cron] Error processing VIP expiration:', error);
        }
    }, {
        timezone: "Europe/Paris"
    });
    console.log('[Cron] VIP Expiration job scheduled (00:00 Paris).');
}

Ce mécanisme repose sur une comparaison temporelle (globalVipExpiresAt < now) et permet une gestion automatisée du cycle de vie des abonnements sans intervention manuelle.

Ce qui a changé depuis cette première version

  • • File d’attente BullMQ / Redis : les changements de rôle ne sont plus appliqués en direct dans la boucle, ils sont mis en file. Au maximum 2 tâches en parallèle et 20 par minute, pour respecter la limite de requêtes de Discord, avec 5 nouvelles tentatives espacées de plus en plus en cas d’échec.
  • • Verrou Redis sur les tâches planifiées : si deux instances du bot tournent, ou lors du changement d’heure, une même tâche ne peut pas s’exécuter deux fois dans la même minute.
  • • Une seule connexion Prisma partagée par tout le code, au lieu d’en créer une par fichier.
  • • Journalisation centralisée : plus de console.log, mais un logger (Winston) qui écrit dans des fichiers en rotation, enregistre les erreurs en base pour le dashboard d’administration et transmet les alertes sur Discord sans le spammer.
